# ai-pipe local performance baseline — 2026-08-21

This document records a provider-free, single-host performance baseline for
JScout on ai-pipe. Its purpose is optimization triage: identify expensive local
paths before changing them, retain the evidence behind each candidate, and give
later implementations a fixed comparison point.

The [machine-readable result](./ai-pipe-2026-08-21.json) is the canonical copy
of the values below. The repeatable harness is
[`bench/perf/ai-pipe.mjs`](../perf/ai-pipe.mjs). This is separate from
`bench/bench-aipipe.py`, which measures retrieval relevance and real model
integrations against a mutable repository database.

The checked-in JSON normalizes retained measurements from the exploratory scripts
that motivated the consolidated harness. The consolidated harness did not emit
these numbers or this JSON. New runs use its `jscout.performance.v1` schema;
compare scenario definitions, fixtures, and timing modes before comparing their
values.

## Scope and non-claims

These are descriptive measurements from one machine and one repository. They
are not CI thresholds, cross-machine estimates, or general product-performance
claims. The filesystem cache was not flushed, host load and thermal state were
not controlled, and no confidence intervals were calculated. A p95 is reported
only for cases with enough retained samples to make it useful.

No remote inference or remote provider was used. Enrichment used the real local
checker sidecar. Embedding used a deterministic loopback HTTP fixture. Scouting
used dry runs or a deterministic fake gateway. Consequently, the results isolate
local preparation, persistence, transport, and SQLite costs; they do not predict
production model latency.

## Method

Timings use a monotonic wall clock. Warmups were discarded, cases were rotated
or interleaved where supported, and measured samples were not selectively
removed. CLI timings include process startup. Persistent MCP timings use one
process and sequential requests; telemetry is integer-millisecond internal tool
time. Profiling used the same source tree compiled in release mode with debug
symbols and frame pointers, but the normal release binary produced the headline
timings.

`/usr/bin/sample` records stack residency, including time blocked in system
calls. The profile percentages below are therefore stack-sample shares, not
pure CPU percentages and not necessarily mutually exclusive.

## Checked harness coverage

The consolidated harness reruns the core scenarios: first and repeated
fresh-database indexing, same-content mtime watch reconciliation, enrichment
planning/full/reuse, lexical CLI search, persistent-MCP round trips, the seven
fixed neighborhood cases, provider-free scouting preparation/publication/reuse,
and embedding population/synchronization/occurrence-index repair.

It does not reproduce every historical diagnostic in this report. In
particular, it does not run or record:

- the 50-run `--version` process-startup control;
- the three-query search limit/response-budget sweep;
- persistent-MCP integer telemetry or aggregate whole-process timing—it records
  per-call MCP round trips instead;
- the `/usr/bin/sample` index, search, and enrichment profiles;
- neighborhood `unbudgeted_bytes`—it records rendered result bytes, graph
  counts, omissions, truncation, and response-hash cardinality.

The schema/index experiments and supplemental seeded semantic-memory/scouting
measurements are also historical follow-ups rather than consolidated-harness
scenarios.

## Baseline results

### Indexing and enrichment

| Path | n | Median | p95 | Qualification |
|---|---:|---:|---:|---|
| New database index | 5 | 535.32 ms | — | Warm filesystem; new application/database state |
| First post-export index | 1 | 776.95 ms | — | Single observation, not a baseline estimate |
| Unchanged watch generation | 11 | 59 ms | — | Same-content timestamp event; excludes 100 ms debounce |
| Full local enrichment | 1 | 330.76 s | — | Real checker; 458 projects and 5,158 occurrences |
| Unchanged enrichment | 5 | 4.52 s | — | 5,158 resumed; zero checker requests |

Four instrumented fresh-index runs placed reference projection at about 27–29%
of total time and structural projection at about 46–48%. Together they accounted
for roughly three quarters of fresh-index time. Those four runs are a separate
measurement set from the five-run 535.32 ms headline.

The full enrichment completed 458/458 projects, selected 5,158/5,158
occurrences, issued 466 checker request batches, and persisted 1,412 resolved
checker-enrichment rows. It was a single long run and must not be read as a
median. The resulting database was 86,269,952 bytes.

The unchanged-enrichment profile contained 3,173 stack samples. The
freshness/reuse path appeared below 3,065 of them and BLAKE3 hashing below 1,824.
The database held 122,303 project-input rows but only 2,093 distinct
`(kind, path, expected hash)` tuples. This is row-identity redundancy, not a
measured 98.3% reduction in filesystem I/O.

### Lexical search

The fixed workload used 24 paraphrased ai-pipe queries, five passes, lexical
retrieval only, no memory, no expansion, and a result limit of 20.

| Path | n | Median | p95 |
|---|---:|---:|---:|
| Process startup control (`--version`) | 50 | 3.569 ms | 3.969 ms |
| CLI search wall time | 120 | 36.165 ms | 47.383 ms |
| Internal BM25 stage | 120 | 1.968 ms | 2.987 ms |
| Persistent MCP internal telemetry | 120 | 30 ms | 35 ms |
| Persistent MCP aggregate wall time | 120 | 32.205 ms/call | — |

The search call-stack profile contained 5,748 samples. `project_chunk_anchors`
was below 2,641 samples, hit loading below approximately 2,316, BM25 below about
301, and `pread` was the top leaf in 2,279. Response budgeting was below 1% of
the sample. Ordinary search serialization was therefore not the primary
bottleneck in this workload.

### Neighborhood

The neighborhood benchmark used a persistent MCP process, five warmups and 50
timed round trips per case.

| Case | Median | p95 | Rendered / unbudgeted bytes |
|---|---:|---:|---:|
| Low-degree default | 0.215 ms | 0.439 ms | 688 / 688 |
| Medium-degree default | 0.178 ms | 0.269 ms | 1,250 / 1,250 |
| High-degree default | 3.533 ms | 4.017 ms | 11,162 / 11,162 |
| Extreme-degree default | 19.054 ms | 20.979 ms | 23,944 / 24,617 |
| High fan-out, complete 100 KB response | 6.236 ms | 6.939 ms | 63,639 / 63,639 |
| Same graph, 24 KB budget | 188.755 ms | 200.113 ms | 23,949 / 63,638 |
| Same graph, 2 KB budget | 208.198 ms | 222.970 ms | 1,887 / 63,637 |

The 24 KB case omitted 58 nodes and 350 edges; the 2 KB case omitted 140 nodes
and 469 edges. The current budget loop removes one edge, prunes nodes, and
serializes again. This is a high-fanout stress-path result, not evidence that
ordinary neighborhood calls are generally slow.

Ten identical, unbudgeted calls in one persistent MCP process produced ten
serialized hashes. The compared variants had the same edge set, but tied
parallel edges appeared in different orders. Under a response budget, that
ordering can also affect which tied edge survives. The exploratory summary was
retained, and the consolidated harness contains the reproduction check, but the
original ten-hash output was not retained. The harness records response-hash
cardinality when it reruns the check. A larger exploratory budgeted run is
deliberately not quoted.

### Embedding synchronization

The historical deterministic `fixture-v1` provider returned 1,024-dimensional
vectors for 5,065 unique chunk hashes and 5,483 chunk occurrences. Its metadata
advertised `normalize = true`, but its dense vector generator did not normalize
the generated values. The checked harness uses a different
`dense-unit-vector-v1` fixture that explicitly unit-normalizes its vectors.

| Path | n | Median |
|---|---:|---:|
| Initial population | 5 | approximately 2.56 s |
| Fully synchronized rerun | 15 | approximately 966 ms |
| Occurrence/vector-index re-materialization from cached vectors | 5 | approximately 2.23 s |

Initial population includes the historical fixture's deterministic Node vector
construction, JSON encoding, loopback HTTP, and 317 requests; it excludes model
inference but is not pure JScout synchronization time. Because the checked
fixture performs different vector work, its population timing is not
method-identical. The synchronized rerun sent no embedding requests and is the
cleaner zero-work measurement. The repair case deleted
`embedding_index_entries` and rebuilt occurrence/sqlite-vec materialization from
cached embeddings; it did not re-embed the corpus.

Automatic card preparation produced 1,024 planned items whose per-item

does not isolate a SQLite transaction, so it only supports the narrower finding
that no material one-card persistence bottleneck was resolved at this precision.

## Measured optimization candidates

### P0: deterministic neighborhood ordering

This is a correctness issue rather than a performance claim. Preserve stable
edge identity through sorting and add a complete content-based tie-breaker,
using database edge ID only as the final fallback.

### P1: graph-node native lookup index

An experimental `graph_nodes(native_id, native_table)` index produced:

| Path | Baseline | Indexed |
|---|---:|---:|
| Persistent MCP internal median | 30 ms | 10–11 ms across three 120-call runs |
| CLI search median | 36.165 ms | 16.621 ms |
| CLI search p95 | 47.383 ms | 20.039 ms |

The index occupied 106,496 bytes. Three fixed equality queries were byte-identical
after excluding MCP initialization. The equality check did not cover all 120
timed calls, and baseline/indexed timing runs were not interleaved, so this is a
workload-specific result rather than a universal 67% claim. The reversed column
order did not provide the selective no-`ANALYZE` query plan.

### P1: composite member-call lookup index

The candidate is `member_calls(file_id, receiver_start, prop)`. Its left prefix
can replace the existing `member_calls(file_id)` index.

| Experiment | Baseline | Composite | Change |
|---|---:|---:|---:|
| Fresh database, four runs/arm | 580.37 ms | 465.80 ms | -19.7% |
| Populated FullRefresh, 12 runs/arm | 647.11 ms | 579.74 ms | -10.4% |
| Reference-projection stage, four runs/arm | 163.87 ms | 96.68 ms | -41.0% |
| Structural projection, four runs/arm | 257.34 ms | 191.45 ms | -25.6% |

Projection-table content hashes matched. The existing file-only index occupied
290,816 bytes. The composite occupied 499,712 bytes when added after population
and 565,248 bytes when maintained during indexing, implying an observed net
replacement cost of approximately 209–274 KB. One exact byte figure would
overstate the storage precision.

### P1: replace one-edge-at-a-time neighborhood shedding

The 30–33× high-fanout budget penalty is measured; a faster retained-prefix or
binary-search implementation is not. Any implementation must preserve stable
ordering, remain under the byte limit, and pass boundary/parity tests.

### P1/P2: cache enrichment freshness hashes per invocation

The 4.52 s unchanged path, stack profile, and project-input multiplicity justify
an implementation experiment. A cache must define behavior if a file changes
during the invocation, and its gain must be measured after implementation. The
current evidence does not prove that all duplicate rows become avoidable reads.

### P2: add a synchronized embedding fast path

The approximately 966 ms zero-request rerun justifies investigation. A fast path
must retain an explicit integrity/repair contract; the baseline does not justify
silently removing the existing sqlite-vec audit.

## Deferred findings

- Ordinary search response serialization was below 1% of the sampled stack.
- A `chunks(name)` index saved about 0.55 ms per exact-name lookup, but was lower
  leverage than the measured candidates above.
- Additional indexes on `refs(file_id, start, id)`, `entity_sites(target_name)`,
  and semantic-artifact run IDs were not justified by this corpus.
- The semantic-history corpus was too small to support a semantic persistence
  index decision.

## Reproduction

The checked harness reruns the scenario subset listed under **Checked harness
coverage**. It does not generate this normalized historical record and does not
reproduce the diagnostics or prior embedding fixture identified there.

```sh
cargo build --release --locked
node bench/perf/ai-pipe.mjs \
  --repo /path/to/ai-pipe \
  --revision ea13166c59cfc52574e96959413f5c54be20e8c8 \
  --binary target/release/jscout \
  --suite full \
  --checker-sidecar checker/src/main.mjs \
  --node-modules /path/to/ai-pipe/node_modules \
  --output /tmp/ai-pipe-performance.json
```

The harness archives the recorded revision, so unrelated working-checkout
changes are excluded. A new result should record its own binary hash, Git
trees, host, toolchain, corpus counts, warmup/sample policy, and whether each
database is fresh, populated, reused, or supplemental.
