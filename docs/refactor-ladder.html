Two constraints worth knowing before you buy any of it

There is still no Rust benchmark harness. No criterion, no [[bench]] target. Allocation removals can be established structurally, but a claimed speedup requires a reproducible release-mode baseline first.

Import grouping cannot be enforced on stable. Verified against 1.97.1: group_imports and imports_granularity both refuse with unstable features are only available in nightly channel. A rustfmt.toml cannot tidy import blocks without a nightly fmt step in CI.

00

Guardrails

Before any file changes. The point is a check that fails loudly on the one thing a bulk move could silently break: a test that stops being compiled and therefore stops running.

  1. Capture the canonical test inventory: cargo test -- --list, sorted, written to a file outside the tree.
  2. Record the baseline: 397 passing, 0 clippy warnings, 0 fmt diffs.
  3. Write the gate script below and run it once against an unmodified tree to confirm it passes.

The gate — run between every commit, not once at the end

# 1. formatting and lints stay at zero
cargo fmt --check
cargo clippy --all-targets -- -D warnings

# 2. every test still compiles, runs, and passes
cargo test --all-targets --all-features

# 3. the inventory is byte-identical to the baseline
cargo test -- --list | sort > /tmp/after.txt
diff /tmp/baseline.txt /tmp/after.txt && echo "inventory intact"

Step 3 is the one that matters for Tier 3. A test module that fails to get wired up after a move still leaves a green cargo test — it just silently stops existing. Comparing the name list catches that; a passing suite does not.

01

Tier 3 — test extraction

shipped · PR #65

18 modules, 18,864 moved lines, extracted from their parent files into sibling files. Each parent keeps #[cfg(test)] followed by mod tests;; the module stays a child of its parent, so private access and cfg gating are unchanged.

Why not foo.test.rs, and why not tests/foo.rs

foo.test.rs is not a Rust form. That is the TS/JS convention. Rust resolves mod name; to exactly name.rs or name/mod.rs — a dotted filename is unresolvable without a #[path] attribute, and nothing in the ecosystem uses that shape.

tests/ means something categorically different. It is the integration test directory: every file there compiles as its own separate crate linking yours as an external dependency, so it sees only the pub API. These tests use use super::* and private items throughout — and jscout has no src/lib.rs, so there is nothing for tests/ to link against in the first place.

Which sibling form — settled by survey, not taste

Two forms are plausible: src/mcp.rs + src/mcp/tests.rs with a plain mod tests;, or a flat src/mcp_tests.rs reached through a #[path] attribute. I surveyed all 1,091 crates unpacked in the local cargo registry to see which one the ecosystem actually uses.

PatternDeclarationsCrates
inline mod tests { … }3,160542
sibling mod tests; → foo/tests.rs225132
#[path = "foo_tests.rs"]11

The flat #[path] form appears once in 1,091 crates. The directory form is what real projects use — tokio, indexmap, ring, wasmparser, simd-json, libm, cranelift. indexmap carries src/map.rs beside src/map/tests.rs and src/set.rs beside src/set/tests.rs. And the objection that a directory holding one file is clutter does not survive contact with the evidence: tokio's src/fs/file/ contains nothing but tests.rs, and it does the same for three more queue modules.

For reference: oxc — jscout's own parser dependency — is 100% inline across 13 test modules. Inline remains the ecosystem default by roughly 14:1; the sibling form is the established exception for files that have outgrown it, which is exactly the case being made here.

// src/io_policy.rs — before
#[cfg(test)]
mod tests {
    use super::*;
    #[test] fn inventory_races_are_not_phase_failures() { … }
}

// src/io_policy.rs — after (identical to tokio and indexmap)
#[cfg(test)]
mod tests;

// src/io_policy/tests.rs — the body, dedented one level
use super::*;
#[test] fn inventory_races_are_not_phase_failures() { … }

Proven, not assumed

I ran the extraction end-to-end on src/io_policy.rs before writing this plan. Parent and sibling coexist without complaint, tests still report under io_policy::tests::* — the module path is unchanged, which is the whole point — and fmt and clippy stayed at zero. The proof-of-concept was reverted; the tree is pristine.

Only where the file was actually hard to navigate

The shipped extraction covered the 18 high-value modules and left smaller inline test modules alone. The resulting sibling files currently contain 18,903 lines after the follow-up tests added in #66 and #67.

Two special cases that break the naive script

1. Not everything under #[cfg(test)] is a test. Eleven files gate production helpers on it — fault-injection hooks like inject_read_failure (indexer.rs:77) and test-only wrappers like index_repo (indexer.rs:175) and compute_snapshot (structural.rs:343). These are members of the parent module, not tests. They must stay exactly where they are. Only mod tests { … } blocks move.

2. main.rs is the crate root, so paths resolve differently. Its test module is named main_tests, and mod main_tests; at the crate root resolves to src/main_tests.rs — not src/main/main_tests.rs. Every other file follows the src/foo.rs → src/foo/tests.rs rule.

Below the floor, and therefore out of scope: llm/process.rs carries a second #[cfg(test)] mod fake test-double module at line 518. Its mod tests block is 233 lines, under the 300-line floor, so the file is not touched at all — and the judgement call about fake never has to be made.

Order of operations

  1. Script the move so it is reproducible, not hand-edited: locate the mod tests { … } block by brace matching, dedent the body one level, write the sibling, replace the block with mod tests;.
  2. Run it one file at a time, gate after each. Eighteen clean gate passes beat one unverified bulk move.
  3. Start with scouting/mod.rs and main.rs — the two that need no new directory, and the two largest wins.
  4. Then the 16 files that need a sibling directory created.
  5. Commit as one commit, message noting it is a pure move, so blame -C has a clean boundary.

Behavioral work — written out, not scheduled

core path

The remaining design refactor is not part of the move-only module work. It deserves its own stacked PRs and behavior-level verification.

4a · The four scout executors

scouting/mod.rs carries four prepare_* / execute_prepared_* pairs — workflow, card, concept, summary. Roughly 1,100 lines, and a direct diff of the workflow and card executors shows about 60% byte-identical.

What actually differs between them is small and enumerable: the kind label string, the subject descriptor, the subject count, the submission type and its SUBMIT_TOOL_NAME, the validate call, and the reuse-report function. Everything else — ledger claim, gateway call, usage JSON, billing-path update, submission parsing, and all four error-report paths — is the same code written four times.

trait ScoutKind {
    type Submission: DeserializeOwned;
    type Prepared;
    const KIND: &'static str;
    const SUBMIT_TOOL: &'static str;

    fn subject_label(prepared: &Self::Prepared) -> String;
    fn subject_count(prepared: &Self::Prepared) -> usize;
    fn validate(…) -> Result<Self::Validated>;
    fn reuse_report(…) -> Result<ScoutReport>;
}

// one executor, four impls — roughly 1,100 lines becomes ~350
fn execute_prepared<K: ScoutKind>(…) -> Result<ScoutReport>
  1. Land Tier 3 first — scouting/tests.rs becomes a 3,291-line file whose test names are the specification this refactor must not break.
  2. Write the trait against the existing four functions without changing them; confirm each of the four can be expressed by it. If any cannot, stop — the abstraction is wrong.
  3. Convert one kind only. card is the best candidate: simplest subject shape, single-subject count, and the densest test coverage.
  4. Gate. Then convert the remaining three one at a time, gating after each.
  5. Delete the four originals only once all four impls are green.

What makes this survivable: 3,291 lines of behaviour-level tests with names that read as specifications — card_publication_loses_the_snapshot_race_without_a_partial_write, gateway_failures_and_cancellation_are_terminal_ledger_states. That is a real safety net. What makes it risky anyway: it is the core scout run path, and the tests cover behaviour, not every interleaving.
