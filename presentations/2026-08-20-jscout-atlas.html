The jscout Atlas

A code index explained the way a newcomer actually asks about it. Every figure is a claim about the real system, drawn from the repository's own numbers — not a schematic of how it might work.

The method: order the pictures by the questions a cold reader asks, in the order they ask them. One claim per figure. Real table names, real line counts, real timings — a diagram you can't falsify is decoration. And end with a map from concepts back to files, because the point of understanding a codebase is knowing where to start reading.

What am I looking at?

Four processes and one file. jscout itself is a single Rust binary (≈67k lines, roughly half inline tests). Everything it knows lives in one SQLite file. Two sidecars do the work Rust can't: a Node process running the real TypeScript compiler, and a Python service producing embeddings. The agent never sees any of this — it talks to the binary over MCP and gets bounded JSON back.

What happens when I run jscout index?

A six-stage pipeline, and the split that matters is between the last two: extraction is incremental — per file, cached by content hash — while projection rebuilds the whole graph from those cached facts on every run. That's why changing a confidence rule costs seconds, not a reparse.

What survives a rebuild?

The database is partitioned by lifecycle, not by subject. Everything cheap to derive from source is dropped and rebuilt every run. Everything that cost money, model weights, or compiler minutes is keyed by content hash and survives — then re-attaches to the fresh snapshot. This is what makes “just reindex” the primary path instead of a migration ladder.

How does a search answer?

Two roads into one ranked response. Identifier-shaped tokens take the deterministic road: exact definitions and whole-token occurrences, retrieved first and placed above everything learned. Everything else goes through the hybrid road — lexical and vector search fused by rank — which is powerful and can be confidently wrong.

What does an edge mean?

Every edge in the graph carries a confidence level and a provenance string. The lattice has three levels, and the single most misread fact in the system is this: no call edge is ever certain — not even one the TypeScript compiler resolved, because one answer from the checker does not mean one possible target.

The second rule of the graph: type information is quarantined, not discarded. Every import is forked at extraction into a runtime list and a contract list, stored in separate tables with no shared join path — a deliberate schema shape instead of a type_only flag, because a flag can be forgotten in a WHERE clause and a table you never join cannot leak.

Where do I start reading?

The map from concepts back to files, sized by line count. One surprise sits in plain sight: the semantic plane — LLM-written artifact generation and retrieval — is the largest region of the codebase, half again the size of the core graph builder it sits on.
