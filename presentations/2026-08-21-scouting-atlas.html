The Scouting Atlas

The part of jscout that spends money. Everything else in the index is derived from source and can be thrown away; scouting sends bounded slices of that index to a language model and keeps what comes back — under rules strict enough that the prose can be trusted as evidence.

Same method as the first atlas: the questions a cold reader asks, in order, one claim per figure, real table names and real numbers. This plane is 24,587 lines — the largest region of the codebase — and almost all of it is enforcement of three rules: the model never chooses what it writes about, every claim carries its own citation, and money leaves the process at exactly one stage.

What does the scout produce?

Five families, one of which isn't an artifact. Repository classification assigns a role to each package, directory area, and TypeScript project; it writes policy rows, and those rows decide which files the other four families are allowed to spend calls on. Workflows and cards read source. Summaries and concepts never do — they read only other artifacts.

What happens in one scout run?

Plan, prepare, execute, publish — the same nine steps for every family. Two of them are the whole cost model: the input fingerprint is computed before the ledger is consulted, so an identical request is reused for free; and a scout_runs row exists in running state before any bytes leave the process, so a crash leaves an attributable row, never a silent charge.

What is an artifact made of?

Three tables and a rule. The artifact row holds the prose as JSON; every field in that JSON is a {text, evidence[]} pair; every evidence entry is a row in semantic_supports pointing at a line range in a file, with the file's hash at the moment of writing. An unsupported claim is not expressible — there is no schema field for one.

How does it know when it's stale?

The same hashes that anchor a claim also age it. Each support carries the evidence file's source_hash and a context_hash of its depth-1 structure; each relation pins the child's artifact_fingerprint. Freshness is computed from those at read time — nothing is marked stale by a watcher — and refresh simply selects what isn't fresh, re-plans it just before execution, and publishes a successor.

How does an agent get to it?

Two MCP routes, both read-only, both bounded. semantic_memory is the direct route: broad discovery returns compact handles, a follow-up reads one body, and every source excerpt is hash-checked against the index before it is shown. semantic_search can attach memory to code hits, but only when an artifact has direct graph or relation evidence connecting it to the returned code — and under budget pressure, memory is shed before code.
